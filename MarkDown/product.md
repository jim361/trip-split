# Trip Split Product Draft

> **[계약 01 · 제품 정의]** 현재 합의된 제품 목표, 대상 사용자와 MVP 범위입니다.

## 1. 제품 한 줄 설명

여행 일정·지도·준비 정보와 실제 지출을 한 여행 세션에서 함께 관리하는 Android 우선 여행 앱.

## 2. 만들고 싶은 문제 해결

여행을 준비할 때 장소는 지도 앱에 저장하고, 일정과 예약은 시트나 메모에 정리하며, 비용은 별도 정산 앱에서 처리하는 경우가 많다. 혼자 여행할 때는 계획과 실제 소비를 함께 보기 어렵고, 여러 명이 갈 때는 누가 결제했고 누가 소비했는지까지 다시 맞춰야 한다.

Trip Split은 여행 장소, 시간표, 지도 동선, 지출 정산을 하나의 Firebase 기반 여행 세션으로 묶어 여행 전후의 번거로움을 줄이는 것을 목표로 한다.

## 3. 초기 타겟

- 2026년 11월 도쿄 여행을 첫 실제 검증 시나리오로 사용한다.
- 혼자 또는 소규모 인원이 함께 쓰는 여행을 같은 데이터 모델로 다룬다.
- 첫 배포 대상은 Android이며 Google Maps와 JPY를 기본으로 검증한다.
- 여행 전 계획, 여행 중 공동 수정, 여행 후 개인 소비와 정산을 한곳에서 확인하고 싶은 사용자

## 4. MVP 방향

초기 MVP는 Flutter stable로 만드는 Android 앱이다. Flutter Web은 Android MVP가 안정된 뒤 계획·검토·공유에 적합한 보조 채널로 검증하며, 첫 배포에서 Android와 기능 동등성을 요구하지 않는다.

- Firebase 기반 여행 세션 생성
- 강제 로그인 없는 비차단 계정 시작 경험
- 내부 Firebase 익명 인증
- 선택적 Google 로그인 연결
- 공유 코드로 여행 참여. Android App Links 초대는 공유 코드 흐름 안정화 뒤 후속
- 공동 편집 사용자인 `TripMember`와 비용 정산 대상인 `Participant`를 분리해 관리
- 여행 이름, 기간, 통화와 예상 인원을 입력하고 예상 인원 기준으로 정산 명단 생성
- Google Places 기반 검색, Google Maps URL 붙여넣기와 직접 입력으로 장소 저장
- 날짜별 시간표 작성
- 일정 순서에 따른 지도 번호 핀과 직선 동선 표시
- ISO 통화 코드와 최소 화폐 단위 정수 기반 실제 지출 입력
- 지출별 결제자, 소비자, 분할 방식, 참여자별 배분 금액 기록
- 전체 균등, 메뉴·항목별 소비자 지정, 공용 메뉴 균등, 참여자별 직접 부담액 입력 지원
- 할인, 봉사료, 기타 조정 금액 배분
- 개인 결제액, 개인 부담액, 받을 금액 또는 보낼 금액 실시간 재계산
- 카테고리별 개인 소비 합계와 날짜·장소·메뉴/지출별 개인 소비 내역 제공
- 정산 공유 문구 복사
- Android 카메라·갤러리의 영수증에서 원문과 한국어 번역을 함께 검토하는 수정 가능한 OCR 항목 초안 생성
- `.trip.json` 내보내기 및 가져오기

MVP에서는 앱이 내부적으로 Firebase Anonymous Auth의 `uid`를 먼저 준비한다. 사용자는 시작 화면에서 `Google로 계속` 또는 `계정 없이 시작`을 선택할 수 있으며, 어떤 선택도 회원가입 장벽이 되지 않는다. 이후 여행을 만들거나 공유 코드로 참여할 수 있고, Google 계정 연결은 같은 익명 uid를 유지하는 설정·복구 기능으로 제공한다.

정산에서는 다음 세 값을 구분한다. 개인 결제액은 자신이 `payer`인 지출의 합계이고, 개인 부담액은 `allocatedAmounts`에 배분된 자신의 몫이며, 정산 결과는 `개인 결제액 - 개인 부담액`이다. 결과가 양수면 받을 금액, 음수면 보낼 금액으로 표시한다.

정산 원장의 canonical `Expense`는 `expenseDate`, `payer { participantId, amount }`, `consumers`, `allocationMethod: equal | itemized | custom`, `allocatedAmounts [{ participantId, amount }]`, `receiptItems`를 기준으로 한다.

영수증 OCR·번역은 Android MVP의 P1에 포함하되, 사용자가 항목과 배분을 검토하고 명시적으로 확정하기 전에는 정산 원장에 반영하지 않는다. Android 카메라나 Photo Picker의 이미지는 Cloud Functions의 provider-neutral `parseReceipt`를 통해 원문·한국어 번역·금액 후보 초안이 된다. 인식에 실패하면 전체 금액 기반 수동 등록으로 전환하며 영수증 이미지는 Firebase Storage에 영구 저장하지 않는다.

## 5. 핵심 사용자 경험

사용자는 비차단 계정 시작을 거쳐 내 여행의 작은 전체 일정 요약을 확인하고, 여행에 들어가 선택 일차의 지도와 순서형 일정을 중심으로 준비·비용 기능을 오간다. 여행 이름, 기간과 인원을 입력해 여행을 만들고 공유 링크나 코드로 공동 편집 멤버를 초대할 수 있으며, 로그인하지 않은 동행도 정산 참여자로 둘 수 있다. 가고 싶은 장소를 검색하거나 Google Maps URL을 붙여넣어 장소 보관함에 저장하고, 저장한 장소를 날짜별 시간표에 배치한다. 여행 중 또는 여행 후에 실제 지출을 입력하면 앱이 결제자와 소비자별 배분 금액을 기준으로 정산 결과를 실시간으로 갱신한다.

개인 정산 화면에서는 내가 먼저 결제한 총액, 이번 여행에서 실제로 소비한 부담 총액, 받을 금액 또는 보낼 금액을 나란히 확인한다. 이어서 카테고리별 개인 소비 합계와 날짜·장소·메뉴 또는 지출별 상세 내역을 확인해, 송금 관계뿐 아니라 이번 여행에서 무엇에 얼마를 소비했는지도 이해할 수 있어야 한다.

제품의 핵심 흐름은 다음 문장으로 정리할 수 있다.

> 장소를 고르면 일정이 되고, 일정에서 쓴 돈이 자동으로 정산된다.

## 6. 공유 및 동기화 방식

초기 MVP는 Firebase 백엔드를 사용해 여행 정보를 저장하고 공유한다. 여행장은 여행을 생성한 뒤 공유 코드를 전달한다. 사용자는 코드로 같은 여행 세션의 `TripMember`가 되고, Firestore 실시간 구독을 통해 일정, 장소와 검증된 지출 변경을 즉시 확인한다. Android App Links 초대는 공유 코드 흐름이 안정된 뒤 추가한다.

기본 공유 흐름은 다음과 같다.

- 앱 접속
- 내부 익명 `uid` 발급
- 여행 생성
- 공유 코드 생성
- 사용자가 코드 입력
- `trips/{tripId}/members/{uid}`에 멤버 등록
- 장소, 일정, 지출 데이터 실시간 구독
- 지출 변경 시 정산 결과 재계산

MVP에서는 공유 코드로 입장한 모든 `TripMember`가 편집 가능한 단순 권한 모델로 시작한다. 보기 전용, 정산만 보기, 관리자 권한, 변경 이력은 이후 확장한다.

첫 공유 코드는 `createTrip`에서 만들고 만료일과 최대 사용 횟수를 설정하지 않는다. 재생성하면 기존 코드를 비활성화하고 새 코드만 활성화한다.

`.trip.json`은 더 이상 핵심 공유 수단이 아니라 백업, 데모 데이터, 데이터 이전, 장애 대비용 보조 기능으로 둔다.

## 7. 해외 우선, 국내 확장

첫 구현은 도쿄 여행을 기준으로 Google Maps, JPY, 일본어 영수증을 검증한다. 통화는 국가에서 자동 확정하지 않고 여행과 지출에 명시하며, 근거 없는 환율로 서로 다른 통화를 합산하지 않는다.

국내 여행과 NAVER 지도는 같은 `PlaceProvider`와 지도 adapter 경계를 사용하는 후속 구현이다. 첫 배포에서는 동작하지 않는 국내/NAVER 선택지를 노출하지 않는다. 지도와 OCR 같은 외부 연동은 provider 방식으로 교체할 수 있게 하되, 첫 버전에서 여러 provider를 동시에 구현하지 않는다.

## 8. 차별점

- 일정과 정산을 따로 관리하지 않는다.
- 장소, 일정, 비용이 하나의 데이터로 연결된다.
- Firebase 기반 실시간 여행 세션으로 여러 명이 동시에 편집할 수 있다.
- 익명 인증으로 진입 장벽을 낮추고, Google 로그인으로 내 여행 목록과 프로필을 보관할 수 있다.
- 결제액, 부담액, 정산 결과를 분리해 대납 관계와 개인 소비를 동시에 설명한다.
- 영수증 전체 균등 분할부터 메뉴별 소비자 지정과 직접 부담액 입력까지 실제 식사·숙소 정산 흐름을 지원한다.
- 공동 여행에서 자주 발생하는 일부 참여, 대리 결제, 운전자 보상 같은 케이스로 확장하기 좋다.
- 도쿄 여행에서 필요한 Google 지도와 JPY 정산 경험을 먼저 깊게 만든다.
- 외부 서비스의 비공개 저장 목록 API에 의존하지 않고 장소 URL과 검색만으로도 일정을 만들 수 있다.
- `.trip.json` 백업으로 Firebase 데이터 이전과 데모 시나리오를 지원한다.

## 10. 후속 검증 항목

- Android App Link 초대를 공유 코드 뒤 어느 시점에 추가할지
- Google Maps URL에서 장소명, 주소, 좌표를 안정적으로 추출할 수 있는지
- 국내 provider를 시작할 때 공식 NAVER API 범위만으로 필요한 장소 흐름을 만들 수 있는지
- OCR 이미지의 일시 전송·처리·폐기 정책을 사용자에게 어떻게 안내할지
- 매우 긴 영수증에서 지출 문서 크기와 항목 편집 성능을 어떻게 제한할지
- 균등 분할의 최소 통화 단위 나머지와 할인 배분 결과를 모든 클라이언트에서 동일하게 재현하는지
- 일본어 OCR 원문과 한국어 번역을 어떤 정확도·비용·보관 기준으로 채택할지
- Android 위치·활동 데이터를 도입할 경우 권한, 배터리와 보관·삭제 정책을 어떻게 설계할지
- 이 프로젝트를 포트폴리오 중심으로 볼지, 실제 서비스 가능성까지 볼지

## 11. 1차 목표

기존 강릉 여행 HTML과 React 목업의 제품 학습을 바탕으로, 여러 여행에 재사용 가능한 Flutter Android MVP를 만든다. 첫 번째 목표는 도쿄 fixture, Google Maps와 JPY를 사용하는 일정·지도, 준비와 수동 정산의 적응형 화면 흐름을 실기기에서 검증하는 것이다. 항목형 OCR·번역은 수동 원장이 안정된 다음 단계로 연결한다.

## 12. 3인 구현 소유권

- 플랫폼·통합: Flutter Android/Firebase 기반, 인증, 여행 생성·공유·멤버, 앱 셸, 공통 UI, 보안 규칙, 백업, 최종 통합
- 정산·영수증: `Participant`, `Expense`, `ReceiptItem`, 순수 Dart 분할·정산 엔진, 개인 소비 화면, 지출 UI, `parseReceipt`와 OCR·번역 검토 흐름
- 장소·일정·지도: Google 장소 검색·URL·직접 입력, 장소 보관함, 일정 편집, 지도 어댑터, 번호 핀과 직선 동선, 준비 화면

기존 Cloud Functions와 Firestore 규칙은 Node.js/TypeScript backend를 유지한다. Flutter 화면과 도메인 코드는 Firebase SDK를 직접 호출하지 않고 mock과 Firebase가 같은 repository 계약을 구현한다.
